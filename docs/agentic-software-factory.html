The Agentic Software Factory

How the software production line changed once agents started writing the code, why removing people from it backfires, and the four-gate workflow Dex Horthy uses to keep code maintainable without giving the speed back.

Drawn from “Ex-NASA dev reveals his Agentic Engineering Workflow” (David Ondrej Podcast, 7 August 2026, 58 minutes, guest Dex Horthy of HumanLayer) and from the Software Factory Playbook skill handed out with the episode. The short version

  1. Agents made building fast. Reviewing stayed slow. The slow part is now trust: knowing that what was built works today and will not slow you down next month.
  2. A factory where nobody reads the code runs well until the first bug the agents cannot fix. Then you spend weeks in code nobody on the team has read.
  3. Models are trained to make tests pass. Nothing in that training penalises a poor design, so maintainable code still needs a person in the loop.
  4. Move that person to the front of the line. Settle the product, the architecture and the program design in short documents, before any code exists and while a change costs one sentence.
  5. Have the agent build in thin end-to-end slices, so there is something to run and re-steer after every step.
  6. Improve the station that limits delivery. Tuning the agent setup is fun and is rarely that station.

The production line, one change at a time

Dex describes software delivery as a factory line that loops: work comes off a list, gets built, checked and shipped, and what users do with it puts new work on the list. Step through the stages below to see which station changes hands at each stage and where the work piles up.

Why you cannot switch the lights off

They can solve problems really, really well, but they’re not going to be able to write maintainable code without you in the loop helping.
Dex Horthy ≈22 min

A lights-off factory is one where no person reads the code. To get there you strengthen every other check: agents that test their own changes, automated review, regression tests, stricter CI, more linters. Dex’s position is that this works for a while and then fails in a predictable way.

Sooner or later a bug appears that the agents cannot fix. You try your strongest prompts, you put three models on it together, and they keep shipping fixes for the wrong cause. Now a person has to go into a codebase nobody has read for months, and both understanding it and finding the fault take days or weeks. ≈9 min

What happened at HumanLayer

Around July 2025 the team ran this way. They reviewed plans and collaborated on tickets, and stopped reading the code. Then a bug hit their desktop app that the agents could not resolve. For weeks the app was buggy and users were unhappy while the team read through code they had never looked at. They dropped the approach afterwards. ≈10 min

Dex’s estimate is that if you stop reading the code, this is more likely to happen to you than not, and more likely than models becoming capable enough to dig you out in time.

Why models write code that passes and still rots

Dex looked into how coding models are trained to find out why this keeps happening. In outline: the model attempts a problem many times, each attempt is scored, and training makes the high-scoring attempts more likely. ≈22 min

The score comes from tests. Do the new tests pass, and does everything that passed before still pass? A clumsy design scores exactly as well as a clean one. That is where habits like wrapping a parse call in a try/catch that only logs and re-throws come from, or type casts scattered around to quiet the compiler. ≈25 min

Training needs an oracle, something that can say quickly whether an attempt was good. Tests answer in seconds. The cost of a bad architectural choice shows up weeks or months later, after many more changes, and there is no practical way to feed that back into a training run. In his words, “maintainability has no fast oracle.” ≈26 min

He adds that the labs are surely working on this and it may be solved. Until then, knowing why models are weak here tells you where your own attention is needed.

What coding benchmarks reward, and what they miss
  • A typical benchmark task is a small historical fix, often one or two hundred lines, graded by hidden tests. A model that scores 99% has shown it can solve problems. It has not shown it writes code you can stop reading. ≈23 min
  • Benchmarks hand over the whole problem at the start. Real software is discovered as you go: ship, hear from users, ship again. Dex says no current benchmark feeds a model a series of features one at a time and scores whether the codebase stayed easy to change. ≈26 min
  • He points to a newer benchmark from Cognition as a step in the right direction. It has a model compare the solution with the human one for equivalent behaviour, a judge that checks the patch against written quality rules, and a check that the tests the model wrote fail on the old code. ≈27 min
The host’s objection: understand the logic, not the code

David Ondrej pushes back on the word “code”. His view is that what you must keep hold of is the logic: what the first five minutes of onboarding look like, what happens when someone cancels, what an endpoint does when it fires. If you know that, you may not need to read every line. ≈11 min

Dex does not argue the point directly. He answers with the four stages in the next section, which are his way of keeping a person in touch with the product, the system and the code at once.

David also describes his own practice: small changes he trusts, such as a front-end tweak, go straight to production. When he is unsure he has a second frontier model review the change and tests more himself. ≈7 min

The four gates

The idea behind all four is leverage: a little time early, to raise the odds that what the agent produces needs few fixes before or after it merges. Two reasons make early the right place. Once hundreds of lines exist, the session is deep in its context window and already leaning the way the model first chose, so changing direction is expensive. A design conversation is small by comparison. Dex shows one that had read the requirements and settled many decisions at about 43,000 tokens, which is where the model reasons best. ≈17 min

In the video these are four stages of alignment, and Dex says they need no particular tool. The packaged skill turns each one into a gate: a document written to disk that you approve before the next one starts. Skill

Gate 1

Product

What user problem are we solving, and how will we know it worked?

You settle

  • The problem, in the user’s words
  • One number that shows success, and how it is measured
  • The announcement: write the blog post before the feature
  • What each screen looks like, as plain HTML mockups

Kept out

  • Databases, schemas, endpoints, file names
  • Any architecture talk

Dex puts the cost at about twenty minutes of back-and-forth, and the return is output that does not need hand polishing afterwards. Writing the announcement first is a practice he credits to Amazon: if you cannot explain to users why it is valuable, reconsider building it. ≈13 min

The document template Skill 
# Product: <feature name>

## Problem
<the user problem, in the end-user's words, not the developer's>

## Success metric
<one real number tied to the business (conversion, latency,
 tickets, revenue) and how it's measured>

## Announcement: the blog post before the feature
<3-6 sentences announcing this feature to users. If you can't
 write it, you're building the wrong thing.>

## Screens
<one line per mockup file in ./mockups/, or "no UI">

Mockups are one plain HTML file per screen, with no framework and no build step. They are meant to be thrown away. Iterate until the answer is “yes, that.”

Gate 2

Architecture

How does this fit into the system we already have?

You settle

  • Which services or modules it touches
  • New endpoints
  • New or changed tables, with outlines of the queries
  • The end-to-end flow on the main path

Who to agree with

  • Whoever would review the pull request
  • On a solo project, yourself, before the code exists

Dex says many people already work this way with models and are comfortable doing so. It is the stage after this one that gets skipped. ≈15 min

The document template Skill 
# Architecture: <feature name>

## Fit
<which existing services/modules this touches, and how>

## Endpoints
<route + verb + purpose, one line each, or "none">

## Data
<new or changed tables/collections, with outlines of the
 queries that will hit them>

## Flow
<the end-to-end call order for the main path: what calls what>

## External
<third-party APIs, env var NAMES (never values), webhooks,
 or "none">

The skill adds one instruction of its own here: read the relevant existing code before writing the document, so the design is made against the real codebase.

Gate 3

Program design

Which decisions would the agent otherwise make silently, halfway through the build?

Before you let the agent go cook, there are decisions that it’s going to make that you might not like.
Dex Horthy, on the step he says most people skip ≈16 min

You settle

  • Where each new or changed file lives
  • Types and method signatures, with no bodies
  • The call stack: what calls what
  • What the tests will assert

Why this form

  • Signatures in a code block can be judged right or wrong in seconds
  • “Why did you put that file there?” gets asked before the file exists

Dex credits an engineer at Cloudflare with ending most of his plans the same way: here is what the tests will look like, and here is the call stack once it is built. ≈17 min

What “signatures without bodies” looks like

An illustration written for these notes. It is not from the video.

// invoices/export.ts   (new file, next to invoices/list.ts)

type ExportRequest = {
  accountId: string
  from: Date
  to: Date
  format: "csv" | "pdf"
}

type ExportJob = {
  id: string
  status: "queued" | "running" | "done" | "failed"
  downloadUrl?: string
}

function requestExport(req: ExportRequest): Promise<ExportJob>
function getExportJob(id: string): Promise<ExportJob | null>

A reader can object at once: should the job live in its own table, should the date range be capped, should PDF wait for a later slice? Each objection costs a sentence now.

The document template Skill 
# Program Design: <feature name>

## Files
<every file created or changed, one line each on why it lives there>

## Types & signatures
<code blocks defining the types and method signatures, NO
 implementation bodies. A human should be able to read these
 in seconds and say "right" or "wrong.">

## Call stack
<for each main flow: what calls what, top to bottom>

## Test plan
<test case names and what each one asserts, before any exist>

## Least confident decisions
<numbered list of the calls most worth challenging now, while
 changing them is free>

The last heading is the skill’s addition. In the video the related tip comes from David: after a change, ask the model which of its choices it is least sure of. Dex’s reply is that program design does the same job before the model runs. ≈17 min

Gate 4

Vertical slices

In what order do we build, so that something runs after every step?

Left alone, models build one layer at a time: all of the database, then the services, then the API, then the front end. Nothing can be tested along the way, and you end up on the far side of thousands of lines hoping they are right. Dex says he has never seen a model choose a different order without a person telling it to. ≈19 min

This is the order Dex used before AI, and the one he now asks the model to follow: ≈20 min

  1. A mock API endpoint
  2. A stubbed front end
  3. The front end made right
  4. Wiring down to the back end
  5. The migration
  6. Business logic
  7. Error handling

Get it working end to end first, then add logic, then add cases. After the first two steps you can already look at the code and decide whether you like where it is heading, and correct it while that is cheap. He credits Matt Pocock, who calls the first thin slice a tracer bullet.

Slice rules and the check after each slice Skill
  • Slice 1 is the tracer bullet. A mocked or hard-coded endpoint and a stubbed screen (or a response you can fetch with curl), wired end to end. It does almost nothing, and it runs.
  • Slice 2 replaces the mocks with real logic for the single happy path.
  • Slice 3 onward: one capability per slice, such as a business rule, error handling, an edge case or polish. Each ends in a working, testable state.
  • Not allowed: building all of one layer before the next.

After every slice the agent proves it works by running it and showing the result, ticks it off in the status file, and asks: “Continue to slice N+1, or re-steer?”

Back pressure: give the agent something to push against

Back pressure is Dex’s word for feedback the agent gets from the thing it built. The more objective that feedback, the further you can let the agent run. From strongest to weakest: ≈13 min

  1. A number tied to the businessConversion on a page, revenue, sign-ups. The agent can try three variants, read the data each day and keep the winner. As David puts it: “If you can tell it a measurable output, the agent will move mountains for you.”
  2. Deterministic checksTests, type checks, linters, CI, complexity limits. Same answer every time, in seconds.
  3. A narrow yes-or-no judgeA model given written rules and a patch, asked only whether the rules were followed. Not deterministic, but steadier than an open review.
  4. Open-ended review by another modelCatches small things and raises the floor. Weakest as a signal about design.
A test that cannot fail tests nothing

Take the tests the agent wrote and run them against the code as it was before the change. If they pass there too, they do not test the change. Dex describes this as a check used in the Cognition benchmark, and notes that agents have been seen commenting out tests to get to green. ≈29 min

The skill makes both into standing rules: never write a test that passes against the old code, and never comment out, skip or weaken a test to make it pass. Skill

Why a second model’s review only goes so far

Dex’s reasoning: if a model could reliably tell good code from bad, it would have written good code the first time, and the models reviewing each other came out of much the same training. Having one model review another’s work does find real issues, and spending more tokens will probably catch all the small ones. It will not stand in for a person’s judgement about design. ≈30 min

He says plainly that he cannot prove this and that it is a shared impression among the engineers he talks to.

What to invest in if you read less code

Reading less code only works if other checks take up the load. The list from the video: ≈8 min

  • Let the agent test its changes live, in a browser or sandbox, and send a short recording when it is done
  • Improve automated code review, for example by running two different models and fixing what both find
  • Strengthen regression testing
  • Each time something fails, find the cause and make that failure impossible to repeat
  • Make CI checks stricter, add linters, monitor complexity
Staying in touch with the codebase

David’s suggestion is to have the agent teach you as it works: quiz you, draw the change as an HTML visualisation, and slow down on purpose when you start to lose your grip. HumanLayer prototyped something similar and did not ship it. While the agent worked, you could open the session and answer multiple-choice questions, with diagrams, on how the code works today and what the new implementation changes. ≈8 min

The skill has a lighter version: if you have not looked at code for a long stretch, the agent reminds you at a slice boundary. Skill

Sending incidents and support requests into the factory

When an alarm fires at night, an agent investigates and has a pull request waiting in the morning. Part of the support queue can be triaged the same way, so that some bugs go straight to an agent. David runs a smaller version: a model reviews every uptime incident and writes a short report on what happened and whether anything can be done, such as “this was the provider” or “a migration is missing”. ≈4 min

Dex’s point about scale: if an agent can handle even 30% of your work or your incidents on its own, that is already a large gain. ≈6 min

Context engineering

Everything you do with a model comes down to what is in its context window. Dex’s rule has three parts: nothing wrong in it, nothing missing from it, and as small as you can make it. The aim is the right tokens, and more of them is not better. ≈37 min

He expects this to hold for as long as models are built on the current attention mechanism: the smaller and more specific the context, the better the result. What has changed is the floor. For an ordinary change he no longer thinks about every token, and he saves that care for hard problems. ≈41 min

Put knowledge in the repository as files

David’s habit on every project, even small ones: ≈33 min

  • docs/adr/ holds decisions, written down explicitly. How pricing launches. That the API schema never changes, and a breaking change ships as /v2.
  • docs/external/ holds what lives outside the code: the names of environment variables (never their values), how the payment processor is set up, which email addresses are used for testing, where customers get in touch.

People on a team carry this knowledge in their heads. A model does not, unless it is written where the model can find it. Dex adds the reason files work so well: reading, writing, editing and searching files is what these models are best at, so knowledge on disk is cheap for them to pick up. ≈34 min

Load context with code, not with instructions

Instructions such as “turn on this server, then here is how you look up recent issues” use up the model’s attention while it is trying to work. If you always want something in context, fetch it with plain code. Dex’s example is a hook that runs when a session starts and pulls in the last ten error reports. That costs processor time and no inference, which leaves the model’s effort for reasoning. ≈35 min

The dumb zone, and when to start a fresh session

The name comes from a training session Dex ran for engineers new to AI coding. With the models of that time, once a session passed roughly half its context window (100,000 to 120,000 tokens) results got worse. His routine was to write everything decided so far into a document and start a new session from that document. ≈42 min

He now calls this training wheels. He regularly runs sessions to 200,000 or 300,000 tokens, and automatic compaction has improved. What remains is the habit underneath: when a session is going badly, one thing to try is starting over and restating the problem.

A related effect he describes in earlier models: as the window filled they began to cut corners and rush, like a student who notices five minutes are left in an exam. ≈44 min

The skill applies the older, stricter form. It writes all decisions into the documents at the end of every gate and every slice and tells you that is a safe point to start fresh. Skill

How tightly to steer

Tell the model how you want something done and you are more likely to get what you had in mind. Leave the how open and the range of outcomes widens in both directions: it may do it badly, and it may find a better way than you would have thought of. Dex treats this as a prompting choice, separate from context engineering. ≈40 min

Where the term comes from

Dex traces it to 12-Factor Agents, a set of principles for building agents that HumanLayer published in spring 2025. The factor that drew most attention was “own your context window”. He says the phrase became widespread a few months later, when Andrej Karpathy and Tobi Lütke began using it, and allows that several people may have arrived at it independently. ≈36 min

Work on the bottleneck

There are inefficiencies that are not bottlenecks.
Dex Horthy ≈46 min

If code review is what limits delivery, adding more coding agents changes nothing. Work only piles up faster in front of review. What counts is value reaching users, measured across the whole line, and a faster station that is not the limiting one does not move that figure.

Dex applies this to “token maxing”, the urge to use up every bit of a subscription. He sees some value in pushing to find the limit and then advises pulling back to what the bottleneck can absorb. His office has a line for it: “Stop playing with your coding agents and get back to work.” Building the thing that builds the thing is enjoyable, and he admits he has been told more than once in his career to stop speeding up CI and ship the tickets. ≈47 min

The question to ask of any improvement is whether it is the bottleneck. If it is not, live with it and put the effort where the constraint is.

The factory story behind it

The idea comes from The Goal by Eliyahu Goldratt, a novel about a manager trying to save a factory. (Dex places the book in the 1970s. It was published in 1984.) In the factories it describes, each machine had someone responsible for keeping it busy, because an idle machine looked like wasted money. Every station was tuned to run flat out. Stations work at different speeds, so one of them is always the slowest, and half-finished work stacked up in front of it, which is expensive to store. Making every station efficient did not make the factory deliver more. ≈45 min

The same point from the host

David’s version: many people spend 80% of each day building tooling and 20% on their real work, and he does not want to be one of them. A setup that is slightly less efficient than someone else’s is fine if the product gets built. He also notes that people have a dumb zone of their own. After three hours on a problem, a walk can show that the problem never mattered to the business. ≈43 min

When to use it, when to skip it

Run the gates

  • People pay for the product and it has to be maintainable six months from now
  • You work in a team, where someone else will review the change (Dex mentions around five engineers and up)
  • Mistakes are expensive: regulated industries, fintech, public companies
  • The change touches several files, adds an endpoint, table or screen, or would produce a diff you would not want to review in one go (the skill puts this at roughly 100 lines) Skill

Skip them

  • You have not found product-market fit and need to put many things in front of customers quickly. Dex calls the full process “probably overkill” here
  • The code is a throwaway prototype Skill
  • The change is trivial: a rename, a typo, a copy or style change, a small config edit Skill
  • You have decided to move fast on this one and said so Skill

The status file is created first. At the start of any session, if one exists for the feature under discussion, the agent reads every document in the folder and continues from the first unapproved gate or the first unticked slice.

The approval routine at each gate
  1. Write the gate document to disk.
  2. Summarise it in five to ten bullet decisions and give the file path. Do not paste the whole document into the chat.
  3. Ask: “Approve Gate N, or what should change?”
  4. Only a clear yes counts as approval. Anything else means revise and ask again.
  5. On approval, mark the gate in the status file and move on.
  6. If later work shows an earlier decision was wrong, stop, update the earlier document, set that gate back to in progress and get it approved again.
Standing rules while the workflow runs
  • Compact at every boundary. Nothing important may exist only in the chat.
  • Keep diffs reviewable. Small slices, and a reminder to look at the code if you have not for a while.
  • Real tests only. No test that passes against the old code. No test weakened to get to green.
  • Optional: when a decision will outlive the feature, record it in docs/adr/. Old records are superseded, never rewritten. Facts about things outside the repository go in docs/external/.

Questions to ask of your own workflow

This list was added while compiling these notes. It restates the ideas above as questions and is not from the video or the skill.

  1. Where are file locations, type signatures and the call stack decided: before the agent starts, or by the agent as it goes?
  2. Is work ordered so that a thin end-to-end version runs first, or layer by layer?
  3. After the first slice, is there a point where a person can look and change direction?
  4. At which points does a person read code, as opposed to plans and summaries?
  5. Does each piece of work have a measurable, deterministic signal that says it is done?
  6. Is anything checking that new tests fail against the old code?
  7. When something goes wrong, does it become a permanent check?
  8. Do decisions, and facts about things outside the repository, have a home on disk?
  9. Which context is loaded by code, and which does the model have to be told to fetch?
  10. What limits delivery right now, and how do you know?

Terms

Software factory
The whole loop that turns a list of work into running software and feeds what users do back onto the list. Agentic when agents staff some of the stations.
Lights-off factory
A factory where no person reads the code. Borrowed from manufacturing plants that run without staff, and so without lighting.
Leverage
Dex’s word for spending a little time early to save a lot later.
Program design
The level below architecture: file locations, types, method signatures, call stack and test plan, agreed before implementation.
Vertical slice, tracer bullet
A thin piece of a feature that runs from screen to data. The tracer bullet is the first one, mostly mocked, built to prove the path works.
Back pressure
Feedback from what was built that pushes back on the agent: a metric, a failing test, a linter.
Oracle
In model training, whatever can say quickly whether an attempt was correct. Tests are one. Maintainability does not have one.
Context window
Everything the model can see at once: instructions, files it has read, the conversation so far.
Dumb zone
Dex’s name for the later part of a long session, where results get worse. His original rule of thumb was about half the window.
Token maxing
Using as much model capacity as possible for its own sake.
ADR
Architecture decision record. A short file stating one decision, its context and its consequences.
